What comes out of a model block, and what goes into it

2026-07-26 new_model_block() output: 4 variants · formula: settled mockups are live — click them

Two separate complaints, one shared cause: the block is trying to answer the analysis when its job is to hand over an object.

The preview shows a coefficient forest plot, so the block reads as "here is your regression". The formula row shows the builder and the text at once, so the same fact is stated twice. Both are cases of the block doing more than its share. Below: four ways to trim the output, four ways to trim the input.

Question one · output preview

The preview should say what's on the wire

The forest plot is not ugly — it's arguably the prettiest thing in the package. But it answers "what does this model say?", and the socket underneath answers "what object comes out?". Those are different questions, and only the second one is the block's. Someone who came here to run an lm() is looking for the thing they'd see in the console; someone who wants the picture should be able to plug a renderer onto the output and get a better picture than a preview can give.

Question two · formula row

Say the formula once

The builder and the text field are two projections of one structure — that's the architecture dev/rich-vs-expr-authoring.md argues for, and it's why they can never disagree. Which is exactly the argument for not showing both: a projection that can't contradict the other adds no information, only height. blockr.dplyr already owns the affordance for this — .blockr-add-link-expr, a 22 × 22 bordered square carrying Blockr.icons.code, sitting in the footer row below the inputs. Same button, same place, one new behaviour: it's a toggle, and it swaps which projection you're looking at.

FX </> below the input, off = click UI, on = formula Built

One row of controls at a time. Off is the resting state and shows the chips; pressing </> replaces them in place with the formula string. The footer row never moves — the button is anchored there in both states, so the toggle stays where your eye left it and the block doesn't jump.

As built — what the drawing didn't say

OrderThe footer is appended last, after both the pill and the text row. Built the other way round first — the row read fine with the chips showing, then stranded itself above the field in text mode.
AlignThe toggle sits hard right, not beside the link — that is summarize's layout (.blockr-add-row is space-between). The drawing above got this wrong; the shipped row adds no geometry of its own.
IconBuilt as a <button> for keyboard access, where summarize uses a <span>. The UA's default button padding squeezed the 14×14 icon to 8×14 — visibly smaller side by side. Zeroed.
HidingIn text mode the link goes by visibility, not display: dropping it out of the flow leaves space-between one item, which slides the toggle to the left edge.
LabelThe old "Formula" caption above the text field is gone. It only ever labelled a row that now appears on request, and dropping it keeps both modes the same height.
SurvThe three-segment pill, its Time / Event / Predictors headers and the event-value gear all hide together — the gear has no formula-text spelling, so it travels with the chips.
StatePressed state is view-only and resets to off on remount, so no R change and nothing new in saved boards. See the open question below.
— Ruled out along the way
DrawerBadge on the pill's right edge that opens the text underneath rather than replacing it. Still shows both at once, which was the original complaint.
SegmentsA Build | Text segmented control. Puts a second row of segments directly under the model-type segments; they read as one broken control.
Text firstFormula as the default with the builder behind the toggle. Inverts the dplyr convention so the same button means the opposite thing two blocks apart.
F4 One line: the chips are the formula Worth prototyping

The reason the two rows feel redundant is that the chip row already reads as the formula, left to right — it's just missing the operators. Put ~ and + between the chips and there is nothing left to duplicate; the badge then flips the same line into an editable string rather than opening a second one. One row, one truth, and the operators become visible objects you can click to change (+ → * → :).

ForRemoves the duplication rather than hiding it. Teaches formula syntax by showing it. Shortest of all four. Interactions stop needing a separate "+ interaction" affordance.
AgainstReal JS work in formula-input.js, not a layout change. The response slot loses its labelled box, so it needs a visual cue that it's the outcome. Long formulas wrap onto several lines.
If you want a route

Cheapest order to do this in

  1. FX — done. inst/js/formula-input.js + inst/css/formula-input.css, no R changes: the widget already keeps one AST and projects both views, so this is purely which projection gets rendered. Verified in the dock board for both the model and survival blocks — the formula text is current in both states whether or not it is showing.
  2. Lift smb_forest() out into a coefficient-plot renderer over the broom tidy frame. It already takes a plain data frame, so this is mostly a move.
  3. Then O3. Once the plot has a home, swap the preview for the object strip plus summary() and drop the toggle. Doing this before step 2 removes a capability instead of relocating it.
  4. F4 as a prototype after the above land, if the single-line formula still looks as good in the widget as it does here.

Open questions

  • Built as view-only, so the toggle resets to off whenever the widget remounts. Worth persisting in block state? A formula-first user would press it once and keep it — but then a saved board reopens in a mode the next person didn't choose, and it stops being a no-R-change feature.
  • + interaction / transform is hidden in the on state, since it's a builder affordance. That does make the footer jump from two items to one. Alternative: keep it, greyed.
  • The survival block shares formula_input_ui() and has a three-segment pill (Time / Event / Predictors). FX carries over unchanged; F4 needs its own answer for the Surv() response.
  • Does the object strip in O3 belong to the model block, or is it generic block chrome that any block returning a non-data-frame object should get?
